---

Go-сервис мониторинга серверов JSOL Team. Каждый узел собирает защищённый HTTP-агент с системными метриками, хранит локальную историю SQLite и использует Redis lease для выбора ведущего экземпляра.

---

## Возможности

| Функция | Пакет | Состояние |
|---|---|---|
| HTTP-агент и системные метрики | `internal/agent` | доступно |
| Мониторинг, интернет-проверки, события | `internal/monitor` | доступно |
| SQLite, история и online backup | `internal/storage` | доступно |
| Lease и выбор узла по приоритету | `internal/cluster` | доступно с ограничениями Redis |
| Telegram меню, карточки, графики, доступы | `internal/telegram` | доступно |
| Docker Compose и публикация GHCR | `.github/workflows` | доступно |

## Запуск одного узла

Нужен Docker Compose v2. Скопируйте `configs/config.example.yaml` в `configs/config.yaml`, задайте адреса агентов и числовые Telegram ID администраторов. Обязательны `node.id`, `storage.sqlite_path`, список `servers` и хотя бы один администратор. Приложение также требует доступный Redis для лидерской аренды.

```sh
cp configs/config.example.yaml configs/config.yaml
export TELEGRAM_BOT_TOKEN='токен от BotFather'
export AGENT_TOKEN='длинный-случайный-секрет'
docker compose up -d --build
```

`AGENT_TOKEN` используется агентом и монитором для заголовка `Authorization: Bearer`. `REDIS_URL` в Compose по умолчанию указывает на локальный Redis; задайте переменную окружения с общим URL для развертывания нескольких узлов. `AGENT_BIND_ADDRESS` по умолчанию ограничивает порт агента loopback-интерфейсом. Для межузлового доступа задайте адрес приватного интерфейса и закройте порт firewall-ом для всех, кроме узлов мониторинга. Redis также оставьте во внутренней сети.

## Несколько узлов

Разверните приложение на каждом сервере с уникальным `node.id`, отдельным путём SQLite и отдельным постоянным volume. Во всех конфигурациях перечислите одинаковый набор наблюдаемых серверов. Каждый экземпляр запускает агент на локальном сервере. Узлам нужен общий Redis.

Узел с меньшим `node.priority` предпочтителен. Узлы регистрируют себя в Redis, лидер продлевает аренду heartbeat. При возврате узла с более высоким приоритетом действующий лидер освобождает аренду и останавливает Telegram polling и мониторинг. При потере связи с Redis лидер также прекращает работу. Если приоритет одинаков, используется лексикографический порядок ID.

Каждый узел хранит свою SQLite локально; базы не открываются по сети. При переключении новый лидер продолжает сбор в своей базе. История и пользовательские доступы между локальными базами не реплицируются, поэтому графики нового лидера могут начинаться с момента его первого запуска. Приложение создаёт online-снимки через SQLite `VACUUM INTO` в `storage.backup_dir` (по умолчанию раз в сутки, хранит 14 дней). Снимок является самостоятельным файлом и может быть перенесён на другой узел после остановки получателя.

Redis остаётся единым арбитром. Аренда защищает от обычной двойной работы при стабильном Redis primary, но не даёт строгого fencing при асинхронном failover Redis или сетевой изоляции. Для строгой гарантии нужен консенсусный координатор с fencing tokens и кворумом.

## Telegram

Создайте бота через BotFather и положите токен в `TELEGRAM_BOT_TOKEN`. Администраторы задаются числовыми ID в `admins`. Пользователь открывает чат командой `/start` после приглашения администратором `/invite @username`; Telegram ID связывается с username из объекта сообщения Telegram. Административные callbacks повторно проверяют права на сервере. Отключение доступа подтверждается кнопкой.

## GHCR

GitHub Actions форматирует и собирает Go-приложение и Docker-образ при push в `main` и при теге `vX.Y.Z`, затем публикует образ в GHCR с SHA, версией и `latest` для основной ветки.

```sh
docker pull ghcr.io/jsolteam/jsol-uptime-bot:latest
docker compose up -d
```

## Ограничения

- SQLite и пользовательские записи остаются локальными и не синхронизируются между узлами.
- Redis lease не является строгим fencing-механизмом при сетевом разделении или failover Redis.
- Журнал показывает последние 10 событий без фильтрации и пагинации.
- Суточная сводка показывает последнее состояние, нагрузку и число инцидентов; точные проценты доступности и длительность простоев не рассчитываются.
- Автоматического восстановления или синхронизации snapshot-истории при выборе нового лидера нет; снимок переносится администратором.
